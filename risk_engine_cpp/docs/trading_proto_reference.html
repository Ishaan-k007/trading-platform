trading.proto — Complete Reference

Trading Platform — gRPC Contract Between Flask/Python and the C++ Engine  |  Created: 2026-07-15  |  Revised: 2026-08-06 — ExecuteOrder migration (see Part 5)

This file is mid-migration. CheckOrder/UpdateState (the original order-execution pair) are being replaced by a single atomic ExecuteOrder RPC because the two-call design has a real, confirmed lost-update race condition — see the deprecation notices on each of them in Part 3, and the migration status checklist in Part 5 for exactly what's done versus still pending.

Part 1: What This File Is, In Plain English

trading.proto is not code that runs. It is a shared vocabulary — a description of the exact shape data must have whenever Python (Flask, the Binance feed handler) and C++ (risk_engine.exe) exchange information. Python and C++ are two completely separate programs that never share memory; the only way they can talk to each other is by agreeing in advance, in writing, on what a message looks like. This file is that agreement.

Both sides run this same file through the protobuf compiler (protoc) and get real, usable code generated from it — actual classes in Python (services/trading_pb2.py) and actual classes in C++ (generated into the CMake build directory). Because both sides generate their code from the identical source file, it is structurally impossible for them to disagree about what a message contains.

The building blocks used throughout this file

ConceptWhat it means
messageDeclares a data structure — like defining a small class with only these fields and nothing else.
= 1, = 2, ...Not a default value or array index. A permanent field tag — an ID number protobuf uses on the wire instead of sending the field name as text every time. Scoped per-message: message A's field 1 and message B's field 1 are unrelated. This is part of why protobuf is smaller and faster than JSON.
repeatedMeans "a list of," not a single value. A repeated PriceLevel field becomes a list-like object on both sides that you can iterate or append to.
enumA closed set of named integer values — e.g. OrderResultCode below. Proto3 requires the first value to be numbered 0 and treats it as the "unset" default, which is why every enum in this file starts with an explicit ..._UNSPECIFIED = 0; entry rather than letting a real outcome silently double as the default.
optionalNormally in proto3, a field that's never set just reads back as its type's zero-value (0.0, "") with no way to tell "never set" apart from "deliberately set to zero." Marking a field optional restores that distinction — it generates a has_<field>() check on both sides, so receiving code can ask "did they actually set this?" instead of guessing from the value.
service / rpcDeclares a remote procedure — a function one process can call on another process over the network. Each rpc line names exactly one request message type and one response message type.
Request / Response pairThe standard shape for every RPC in this file: one message travels out to the callee, a different message travels back. Same pattern as a function's arguments and its return value, just over a network instead of in-process.
Every RPC in this file is unary — one request, one response, no streaming. This matches the actual traffic pattern needed: even the highest-volume RPC (UpdateOrderBook, at full symbol-universe scale) is on the order of a few thousand calls/second, which a plain unary call over an already-open gRPC connection handles comfortably. Streaming RPCs exist in gRPC but were deliberately not used here — they solve a different problem (very high-frequency continuous push, or client-finishes-then-gets-one-summary) that doesn't apply to any current use case.

Part 2: Shared Building Blocks

PositionEntry

Used inside LoadUserRequest

Represents one holding a user has in one symbol — not sent on its own, only ever as part of a list inside a bigger message.

FieldTypeMeaning
symbolstringTicker, e.g. "AAPL"
quantitydoubleHow many shares/units are held
average_pricedoubleAverage cost basis for this position
Example instance: { symbol: "AAPL", quantity: 10, average_price: 182.50 }

PriceLevel

Used inside OrderBookUpdateRequest

Represents one row of an order book: at this price, this much quantity is resting. Like PositionEntry, it is a building block — never sent alone, always as part of a repeated list.

FieldTypeMeaning
pricedoubleThe price at this level
quantitydoubleTotal quantity resting at that price
Example instance: { price: 67200.50, quantity: 0.42 }
  — meaning: someone has an order for 0.42 BTC at $67,200.50

OrderResultCode (new)

Used inside ExecuteOrderResponse

Replaces the old bool approved + free-text reason pattern from CheckOrderResponse. That pattern is what let a LIMIT order that simply didn't cross the market get reported to the user as "insufficient funds" — Python had no reliable way to distinguish rejection reasons other than string-matching free text that was never actually checked (see the CheckOrder deprecation notice in Part 3). A typed enum makes each outcome a distinct value the caller can switch on instead of guessing.

ValueNumberMeaning
ORDER_RESULT_UNSPECIFIED0Never a real outcome — proto3's required zero-value. Seeing this on the wire means the field was never set, which is itself a bug.
FILLED1Order executed. fill_price, new_cash, new_quantity are populated.
UNKNOWN_SYMBOL2Symbol isn't tracked by the price store or order book.
LIMIT_NOT_MET3LIMIT order's price never crossed the market — not a funds/position problem.
INSUFFICIENT_FUNDS4BUY rejected — not enough cash. required_cash/available_cash populated.
INSUFFICIENT_POSITION5SELL rejected — not enough held quantity. required_quantity/available_quantity populated.
INVALID_ORDER6Malformed request — bad side/order_type, non-positive quantity, etc.
IDEMPOTENCY_CONFLICT7Same client_order_id seen before, but with different order details (symbol/side/quantity) — a retry can't be assumed safe when the request itself changed.
INTERNAL_ERROR8Engine-side failure unrelated to the order itself (e.g. WAL write failed).
Intended Python-side mapping (services/risk_engine_client.py): each non-FILLED code raises a distinct core.exceptions.TradingError subclass instead of the current one-size-fits-all InsufficientFundsError/InsufficientPositionError branching. Not implemented yet — this is the target design, tracked as its own migration step.

The Four Identifiers (new)

user_id, client_order_id, order_id, event_id — used across ExecuteOrderRequest/Response

Four different IDs travel through one order. They are not four names for the same thing — each answers a different question, at a different point in the pipeline, and merging any two of them removes a real guarantee.

IdentifierAssigned byAnswers
user_idAlready exists (the account)"Whose account is this against?" — not really part of the order-identity story at all; it's what selects which per-user lock and UserState to touch in user_state_store.cpp.
client_order_idThe calling strategy/client, before the request is ever sent"Did I already send this exact request?" Stays identical across a client's own retries (e.g. after a dropped connection), which is what makes deduplication possible. Must never be replaced with a server-generated value before it reaches the WAL — doing so is what currently makes idempotency impossible end-to-end, see Part 5.
order_idC++, once an order is accepted"What do I call this order for the rest of its life?" A permanent, globally-unique, server-generated identity — the primary key for the orders table row, and what RiskCheck/LedgerEntry foreign-key against. Server-generated (not client-supplied) because a client's own id is only guaranteed unique to that one client — two different strategy bots could independently choose the same string.
event_idC++, once the WAL entry is written"Did I already process this delivery?" — a different concern from the order itself. Kafka's at-least-once delivery guarantee means fill_consumer.py can receive the same message twice even though the order was only ever executed once. event_id lets the consumer recognize a redelivered event and skip it, independent of whether the order was retried.
What breaks if two of these are merged into one:
  • client_order_id merged into order_id (client picks the permanent id) — two strategies can collide on the same string and silently share/overwrite each other's order row.
  • order_id merged into event_id (one id for "the order" and "this log entry") — breaks the moment an order can produce more than one event (e.g. a future partial-fill feature).
  • event_id dropped, deduping on client_order_id alone — a Kafka rebalance redelivering the same message looks identical to a legitimate new order; fill_consumer.py could double-apply a fill to the cash balance.

Part 3: Every RPC, In Detail

1. ExecuteOrder (new — replaces CheckOrder + UpdateState)

Called by: Flask (order_service.py)  →  Answered by: C++ risk engine

What it's for: Executes an order atomically in a single RPC — validates, prices, checks funds/position, writes the WAL entry, and applies the resulting state to the in-memory user record, all under one held per-user lock, acquired once and released only after either a rejection is returned or the WAL succeeds and state has been applied. This collapses the CheckOrder → (Python round-trip) → UpdateState flow down to zero gap — there is no longer a window between "compute the new state" and "commit it" for a second concurrent order to land in.

ExecuteOrderRequest

FieldTypeMeaning
client_order_idstringCaller-supplied, stable across retries — see "The Four Identifiers" above
user_idint32Who is placing the order
symbolstringWhat's being traded
sidestring"BUY" or "SELL"
order_typestring"MARKET" or "LIMIT"
quantitydoubleHow much to trade
limit_pricedoubleOnly meaningful for LIMIT orders
Deliberately absent: any new_cash/new_quantity-style field. This request cannot carry a resulting balance even if a caller wanted it to — the field doesn't exist. Python owns request transport and presentation; C++ owns execution price, the risk decision, and the state mutation. This is what makes it structurally impossible to reintroduce the old bug where Python computed (or mis-computed) a balance and told C++ to accept it.

ExecuteOrderResponse

FieldTypeMeaning
resultOrderResultCodeTyped outcome — see above
client_order_idstringEchoed back unchanged, for the caller to match against its own retry
order_idstringCanonical server-generated order identifier
event_idstringIdentifier for the committed WAL/Kafka event
fill_price, market_priceoptional doubleOnly meaningful when result == FILLED
required_cash, available_cashoptional doubleOnly meaningful on INSUFFICIENT_FUNDS — lets Python report the real shortfall instead of computing (and potentially miscomputing) its own
required_quantity, available_quantityoptional doubleOnly meaningful on INSUFFICIENT_POSITION
new_cash, new_quantityoptional doubleNew balances after a fill, for display only — Python must never send these back on a later request
account_sequenceuint64Running per-user counter, incremented on every applied state change
messagestringHuman-readable detail, for logs — not something calling code should branch on; that's what result is for

Connects to: the WAL entry is written inside the same locked critical section as the state mutation, before the lock is released — unlike the deprecated flow, there is no path where a mutation is applied in memory without a corresponding WAL entry existing. From there, the same downstream pipeline as before: pipeline/wal_producer.py → Kafka order-fills topic → pipeline/fill_consumer.py → PostgreSQL.

Status: contract defined only. This message shape exists in the .proto and stubs can be regenerated from it, but there is no C++ handler in trading_service.cpp yet, no split evaluate/apply logic in user_state_store.cpp, no dedupe map, and no Python client method. See Part 5 for the full checklist.

2. CheckOrder Deprecated

Called by: Flask (order_service.py)  →  Answered by: C++ risk engine

Deprecated: replaced by ExecuteOrder. Despite its name, this RPC does not only check — it fully mutates user.cash/user.positions inside check_and_reserve_position, releases the per-user lock, and returns the result to Python before anything is confirmed or persisted. Because the lock is released here and re-acquired later inside a separate UpdateState call, there is a real window — spanning a full Python round-trip — where a second concurrent order for the same user can be evaluated against state that is about to be overwritten. Two orders for one user, interleaved across their CheckOrder/UpdateState pairs, can silently lose one trade's effect on the cash balance with no error raised. Left in place, not deleted, so nothing still depending on it breaks mid-migration — new code must call ExecuteOrder instead.

What it was for: Before any trade was allowed to happen, Flask asked the C++ engine "can this user actually do this?" — checking funds for a BUY or held quantity for a SELL — entirely from in-memory state, no database round trip.

CheckOrderRequest

FieldTypeMeaning
user_idint32Who is placing the order
order_idstringIntended as a client-supplied unique ID, but nothing downstream of this call actually preserves it — see the identifier note in Part 5
symbolstringWhat's being traded
sidestring"BUY" or "SELL"
order_typestring"MARKET" or "LIMIT"
quantitydoubleHow much to trade
limit_pricedoubleOnly meaningful for LIMIT orders

CheckOrderResponse

FieldTypeMeaning
approvedboolCan this order proceed?
reasonstringFree-text rejection reason — never actually inspected by order_service.py, which is why a LIMIT-not-met rejection currently gets reported to the user as "insufficient funds"
risk_scoredoubleField exists but nothing ever sets it — no scoring model has been implemented
fill_pricedoubleNever set on a rejection, which silently defaults to protobuf's zero-value 0.0 — combined with the reason bug above, this is why a rejected order can currently report "requires $0"

Connects to: If approved is true, Flask immediately calls UpdateState to actually apply the trade. If false, order_service.py raises InsufficientFundsError or InsufficientPositionError unconditionally based on order side, regardless of what reason actually says.

3. UpdateState Deprecated

Called by: Flask, immediately after an approved CheckOrder

Deprecated: replaced by ExecuteOrder. This is the other half of the CheckOrder/UpdateState race condition: it unconditionally overwrites user.cash/user.positions with whatever absolute values Python sends, on the assumption that Python is echoing back exactly what CheckOrder told it — rather than C++ computing the result itself from current state at the moment of commit. If two orders for the same user are in flight, whichever UpdateState call lands last wins, even if its snapshot is now stale — silently undoing the other order's effect on the balance. Left in place so nothing still depending on it breaks mid-migration — new code must call ExecuteOrder instead.

What it was for: Committed an approved trade into the engine's in-memory state (new cash balance, new position) and wrote a Write-Ahead-Log entry — this was the only place a trade became "real" inside the engine. No PostgreSQL write happens here or anywhere in this path; persistence happens later, asynchronously, via the WAL → Kafka → fill_consumer.py pipeline.

UpdateStateRequest

FieldTypeMeaning
user_idint32Whose state to update
symbolstringWhich symbol was traded
new_cash_balancedoubleCash balance after this fill — computed by Python, from the snapshot CheckOrder returned, not recomputed here
new_quantitydoublePosition size after this fill
new_average_pricedoubleUpdated cost basis
order_id, side, fill_price, quantity, order_typemixedFull fill details — included so the WAL entry written from this call is complete on its own, without needing to look anything else up

UpdateStateResponse

FieldTypeMeaning
successboolDid the update apply
messagestringHuman-readable detail

Connects to: the WAL entry written here is later read by pipeline/wal_producer.py and published to Kafka's order-fills topic, eventually landing in PostgreSQL via pipeline/fill_consumer.py.

4. LoadUser

Called by: Flask, only the first time a user is seen

What it's for: The C++ engine holds trading state in RAM, not the database — but RAM is empty on startup. The first time a given user places an order, Flask reads their current cash and positions out of PostgreSQL and hands them to the engine once, so every subsequent order for that user is answered from memory with no DB read.

LoadUserRequest

FieldTypeMeaning
user_idint32Who to load
cash_balancedoubleStarting cash, from the accounts table
positionsrepeated PositionEntryAll current holdings, from the positions table

LoadUserResponse

FieldTypeMeaning
successboolDid the load apply
messagestringHuman-readable detail

Connects to: gated by HasUser (below) — Flask always checks HasUser first and only calls LoadUser if the answer is no. This pair together is the "write-through cache" pattern. Unaffected by the ExecuteOrder migration — this stays exactly as it is.

5. HasUser

Called by: Flask, before every order, to decide whether LoadUser is needed

What it's for: A cheap yes/no check — "is this user already sitting in your memory?" Exists purely to avoid an unnecessary PostgreSQL read on every single order; only the very first order for a given user pays that cost.

HasUserRequest

FieldTypeMeaning
user_idint32Who to check

HasUserResponse

FieldTypeMeaning

6. GetPrice

Called by: Flask market_routes.py (GET /prices/<symbol>), and internally by order_service.py

What it's for: Returns the current price the engine is using for one symbol, read from the live order book when one exists (falling back to the seeded PriceStore otherwise). Kept as a separate read-only informational RPC from order execution — ExecuteOrder does its own internal lookup against the same underlying store rather than requiring this to be called first.

GetPriceRequest

FieldTypeMeaning
symbolstringWhich symbol

GetPriceResponse

FieldTypeMeaning
symbolstringEchoed back
pricedoubleCurrent price
updated_atstringTimestamp of the last update
best_bid, best_askdoubleTop of book, when live order-book data is available
If the symbol was never seeded into the engine, this RPC returns a gRPC NOT_FOUND status, which risk_engine_client.py turns into a SymbolNotFoundError.
Known minor issue: best_bid and best_ask are read via two separate calls into OrderBook (best_bid() then best_ask()), each independently acquiring and releasing the book's lock. If the order book updates between the two calls, the response can mix a bid from one snapshot with an ask from a slightly later one. Low real-world impact at current update frequency; tracked as a fix (read both under one lock acquisition) rather than left silent.

7. GetAllPrices

Called by: Flask market_routes.py (GET /prices)

What it's for: Same idea as GetPrice, but for every symbol at once — powers the "all current prices" market data endpoint.

GetAllPricesRequest

Empty — no input needed, it's "give me everything you have."

GetAllPricesResponse

FieldTypeMeaning

Called by: the Binance feed handler (pipeline/orderbook_feed_producer.py), once per depth snapshot

What it's for: Delivers one real order book snapshot for one symbol — Binance's top-of-book bid/ask levels — from the Python feed handler into the C++ engine's memory.

Part 4: How The RPCs Fit Together — End to End

Order placement flow — deprecated (still what the code does until Part 5's checklist is complete)

Flask receives POST /orders
   → HasUser?           (cheap check: is this user already in memory?)
       → no  → LoadUser  (one-time: pull cash + positions from Postgres)
   → CheckOrder          (mutates state immediately, releases lock, returns a snapshot)
       → approved? → UpdateState   (Python echoes the snapshot back; overwrites state again)
                   → (async, off this path) WAL → Kafka → Postgres

   ⚠ the gap between CheckOrder returning and UpdateState landing is where the
     lost-update race condition lives — see the deprecation notices in Part 3.

Order placement flow — target

Flask receives POST /orders
   → HasUser?           (cheap check: is this user already in memory?)
       → no  → LoadUser  (one-time: pull cash + positions from Postgres)
   → ExecuteOrder        (one call: lock → dedupe check → price → validate →
                           evaluate → write WAL → apply state → unlock → return)
                   → (async, off this path) WAL → Kafka → Postgres

   No gap between "compute the new state" and "commit it" — both happen
   under one held lock, inside one RPC.

Market data flow

Browser / researcher hits GET /prices or GET /prices/<symbol>
   → Flask calls GetAllPrices or GetPrice
   → reads the live OrderBook store when populated, falling back to the seeded PriceStore

Real market data ingestion flow

Binance WebSocket (partial-depth stream)
   → Python feed handler parses the JSON snapshot
   → builds an OrderBookUpdateRequest
   → calls UpdateOrderBook over gRPC
   → C++ stores it in the OrderBook class
   → GetPrice / ExecuteOrder's internal price lookup both read from there
